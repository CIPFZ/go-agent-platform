# 项目背景与决策

## 背景

GoWebFrame CMS 已经具备在 Ubuntu/QEMU 环境中创建和管理虚拟机的能力。这些虚拟机除了部署用途，还需要为 Agent、自动化任务和测试流程提供一个可以被安全操作的运行环境，例如执行命令、截图、收集文件和进行桌面操作。

如果把这些能力继续放进 CMS，虚拟机生命周期、任务调度、结果存储、审计和安全策略会互相耦合，后续也难以把同一套 Agent 用到其他虚拟机来源。因此本项目单独建立为一个 Go 服务和一个虚拟机内 Agent。

## 已确定的决策

### 独立仓库

项目仓库为 `CIPFZ/go-agent-platform`，与 GoWebFrame CMS 分开维护。CMS 通过稳定的 HTTP API 使用 Agent 能力，不直接依赖 Agent 的 Go 包和内部实现。

### Ubuntu 是首个运行和验证环境

首个 Gateway 工作副本位于 Ubuntu：`/home/ytq/work/go-agent-platform`。它靠近 QEMU、虚拟机和 CMS，适合做 Linux 构建、镜像安装、systemd 运行以及连通性验证。本机保留一个 Git 工作副本，用于设计、编辑和查看变更；GitHub 是正式源仓库。

### Agent 使用 HTTP/HTTPS

虚拟机中的 Agent 只需要主动访问 Gateway，不采用 SSH 作为项目的连接管理方式。这样各类 VM 使用统一的端口和协议，也不需要为每台 VM 维护 SSH 连接状态或暴露入站服务。

### rdev 只作为设计参考

`/Volumes/workspace/project/rdev` 中关于任务 ID、幂等、队列、有界并发、超时、取消、输出限制、能力探测、后台任务和审计的经验可以借鉴，但本项目不复用 rdev 的 SSH 传输、Agent、内部包或项目目录。

## 目标

1. 为每台虚拟机提供一个可注册、可观测、可撤销的 Agent 身份。
2. 通过统一 HTTP API 提交命令、截图、文件和桌面操作任务。
3. 在高并发、网络抖动和任务失败时保持状态可追踪，避免重复执行和无限等待。
4. 对危险操作提供策略拦截、风险提示、确认信号和完整审计。
5. 让 CMS 只依赖 Agent Gateway 的稳定接口，而不承担执行细节。

## 明确不做的事情

- 不在这个项目中管理 QEMU 虚拟机的创建、删除、磁盘和网络生命周期。
- 不把 CMS 前端、CMS 数据库模型或 CMS 的内部服务搬进本仓库。
- 不把任意字符串直接作为 root shell 执行接口暴露给调用方。
- 不因为参考 rdev 就引入 SSH 会话池或复用 rdev 的内部实现。

## 下一 session 的默认起点

下一次继续开发时，优先实现 Gateway 与 Agent 的第一版协议：注册、心跳、能力摘要、任务提交、任务拉取、结果回传和优雅离线。完成后再进入命令执行和截图能力，避免一开始就把功能和传输、状态模型绑死。
