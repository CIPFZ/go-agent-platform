# 网页远程桌面：功能与方案设计

状态：第二稿。已记入 2026-11-15 的讨论决定（第 8 节）与 Windows 笔记本上的实测结果（第 3.4 节）。本文未改动任何代码。定稿后相关内容并入 [`spec.md`](spec.md) 作为阶段 4。

## 0. 摘要

目标：在浏览器里打开一个网页，就能看到并操作装有 `vm-agent` 的 Windows 桌面，体验尽量接近坐在真机前，笔记本合盖时也能用。

结论：

1. 可行，并且 `vm-agent` 已具备一半基础（输入注入、光标图像、剪贴板、ffmpeg 进程管理、会话检测）。缺的是连续视频、实时输入通道和网页端。
2. 方案：ffmpeg 采集并编码 H.264，经 WebRTC（纯 Go 的 pion）推给浏览器的 `<video>`；鼠标键盘经 WebRTC 数据通道回传，直接调用现有输入后端。
3. 实测发现一个决定体验上限的问题：笔记本合盖时系统停止画面合成，首选的桌面复制采集拿不到任何一帧，只有 GDI 采集可用，实际约 16 帧每秒。要在合盖状态下达到 30 帧以上，必须给系统一个"活动的显示器"：虚拟显示驱动或 HDMI 假负载。RustDesk 遇到的是同一个限制，它的解法也是虚拟显示驱动。详见 3.4 与 5.11。
4. 范围已确定：只做 Windows；包含声音；包含锁屏与 UAC（需要系统级组件）；同一时间只允许一个使用者。
5. 比不上 RustDesk 的地方：文字边缘的清晰度（硬件 H.264 是 4:2:0 色度）、部分系统快捷键（受浏览器限制）。详见第 6 节。

第 8 节是已确定的决定和还剩下的两个问题。

## 1. 目标与非目标

目标：

- 浏览器访问，不安装客户端；首选 Chrome 与 Edge。
- 局域网内使用，30 帧每秒以上，操作延迟低到不影响日常使用（目标：点击到画面变化 100 毫秒左右）。
- 本期只做 Windows；Linux 以后再议。
- 笔记本合盖是日常使用状态，必须可用。
- 人和 Agent 共用同一个桌面：人在网页上能看到 Agent 的操作并随时接管。
- 保持单二进制、纯 Go、`CGO_ENABLED=0`，三平台交叉编译不变。

非目标（本期不做）：

- 公网穿透、中继服务器、账号体系。
- 鉴权与 TLS（沿用 D9；只在自己的局域网内使用）。
- Linux（X11 与 Wayland）。
- 移动端浏览器的触控适配。

## 2. RustDesk 的做法

依据 RustDesk 源码 `fcb485b`（2026-11-15）。路径相对其仓库根目录；`hbb_common/` 指独立的公共库仓库。

### 2.1 视频

| 环节 | 做法 | 出处 |
| --- | --- | --- |
| Windows 采集 | 首选 DXGI 桌面复制；连续拿不到帧或出错时回退 GDI；`ACCESS_LOST` 在 10 秒内最多重建 3 次，之后回退 GDI | `src/server/video_service.rs:70-74`、`:912` |
| Linux X11 采集 | xcb 共享内存（`xcb_shm_get_image`） | `libs/scrap/src/x11/capturer.rs` |

| 编码器选择 | 双方协商；自动模式优先级为 H.265、H.264（仅当有硬件编码器）、否则 AV1 或 VP9 软编码 | `libs/scrap/src/common/codec.rs:271-290` |
| 码率 | 按分辨率查基准码率（1080p 约 2073 kbps，2K 约 3000 kbps），再乘画质系数：最佳 1.5、平衡 0.67、流畅 0.5 | `libs/scrap/src/common/codec.rs:893-895`、`:929` |
| 码率控制与关键帧 | CBR；不发周期性关键帧（VPX 关闭关键帧模式，硬件编码 GOP 设为最大整数），只在需要时刷新 | `libs/scrap/src/common/vpxcodec.rs:89`、`:94`；`hwcodec.rs:33`、`:246` |
| 帧率 | 新连接从 15 帧起步，默认目标 30，上限 120，自动调节下限 5 | `src/server/video_qos.rs:51-55` |
| 自适应 | 在视频流里插入延迟探测包；超出基线 150 毫秒算拥塞，先降码率再降帧率；每 3 秒调整一次画质系数 | `src/server/video_qos.rs:9-49`、`:63-67` |
| 流量控制 | 每发一帧，等所有观看端回执后才发下一帧，最长等 3 秒 | `src/server/video_service.rs:1010-1021` |
| 静止画面 | 画面不变时用同一帧重复编码，让画质逐步变清晰 | `src/server/video_service/static_refresh.rs` |

### 2.6 对我们的启示

| RustDesk 的做法 | 我们 | 原因 |
| --- | --- | --- |
| DXGI 桌面复制采集 | 采用（通过 ffmpeg 的 `ddagrab`） | 同一套系统接口，不需要自己写 COM 调用 |
| 硬件 H.264 优先 | 采用 | 浏览器对 H.264 硬解支持最好 |
| 光标形状与位置独立传输、本地绘制 | 采用 | 对手感影响最大，而且 `vm-agent` 已能取光标图像 |
| 按键位置码（Map 模式） | 采用 | 浏览器的 `KeyboardEvent.code` 正好是位置码 |
| 断开时释放已按下的键 | 采用 | 否则会出现卡住的 Ctrl、Shift |
| 视频走可靠流、应用层回执流控 | 不采用，改用 WebRTC 媒体轨道 | 浏览器里自带抖动缓冲、丢包重传和硬解，省掉自己实现 |
| 协商多种编码、自适应码率 | 第一版不做，固定参数 | 局域网带宽充足；ffmpeg 命令行运行中改不了码率 |
| 系统服务处理锁屏与 UAC | 采用，放在阶段 4（5.14） | 需要改变运行架构并以管理员安装 |
| 虚拟显示驱动解决无显示器 | 采用，放在阶段 3（5.11） | 合盖时系统不合成画面，实测见 3.4 |
| 中继、打洞、账号、加密握手 | 不做 | 局域网使用，不在目标内 |

### 3.2 现有设计里不适用的部分

| 现状 | 问题 | 处理 |
| --- | --- | --- |
| 截图走 GDI `BitBlt` 加 JPEG，2560×1600 实测每帧 100 到 170 毫秒 | 做不了 30 帧 | 视频不走截图路径，改由 ffmpeg 采集编码 |
| 每个请求占一个并发名额、硬超时 10 分钟、结束时写一条审计 | 远程会话是长连接 | 会话生命周期独立于请求，只有建立与关闭是请求 |
| 输入动作带人为延时（点击按住 10 毫秒、移动插值） | 实时操作不需要 | 实时通道直接调用后端原语，仍与 Agent 的输入共用同一把队列锁，保证不交错 |
| 滚轮只接受整数刻度 | 触控板滚动不顺滑 | 后端增加按原始增量滚动的入口 |
| 只有 JSON 接口，没有静态页面 | 需要提供网页 | 用 `go:embed` 内嵌页面，新增 `/remote/` 路径 |
| 没有 WebSocket 或 WebRTC 依赖 | 需要实时通道 | 引入 pion（见 5.2） |

### 3.4 实测结果（2026-11-15，笔记本合盖状态）

测试方法：通过 `vm-agent` 在笔记本上运行 ffmpeg，每项 6 到 8 秒，输出丢弃。桌面内容基本静止（一个终端窗口）。

| 项目 | 结果 |
| --- | --- |
| 桌面复制采集（`ddagrab`），共 8 次、多种参数 | 全部卡住：能打开输出（2560×1600），但一帧都拿不到，直到超时被终止。期间移动鼠标、让任务栏重绘也没有帧 |
| 系统合成状态 | `DwmGetCompositionTimingInfo` 返回失败（0x88980090），一秒内垂直同步次数为 0；没有处于活动状态的显示器；合盖动作设置为"不采取任何操作" |
| GDI 采集（`gdigrab`），只采集不编码 | 实际 16 帧每秒（6 秒 98 帧）；CPU 占用很低，说明是在等系统，不是算不过来 |
| GDI 采集加 `libx264 ultrafast`，原生分辨率 | 输出 30 帧，其中约一半是重复帧；CPU 约 1.7 个核 |
| GDI 采集加 `h264_qsv` 硬件编码 | 同上的帧率；CPU 约 0.9 个核 |
| GDI 采集，缩到 1280×800 再软件编码 | 同上的帧率；CPU 约 0.8 个核 |
| `h264_qsv` 编码能力（合成画面，不含采集） | 2560×1600 下 109 帧每秒 |
| `libx264 ultrafast` 编码能力（同上） | 约 400 帧每秒，占用多个核 |
| 现有截图接口（GDI 加 JPEG） | 每帧往返 100 到 170 毫秒 |
| 输入注入 | 合盖状态下正常 |

同一天开盖亮屏后补测（2560×1600，每项 6 秒）：

| 管线 | 帧率 | CPU 占用 |
| --- | --- | --- |
| 桌面复制，只采集 | 58 帧每秒 | 约 0.04 个核 |
| 桌面复制 → 显存内直接交给 `h264_qsv`（不经过内存拷贝），60 帧 | 55 帧每秒 | 约 0.25 个核 |
| 桌面复制 → 下载到内存 → `h264_qsv`，60 帧 | 55 帧每秒 | 约 3.3 个核 |
| 桌面复制 → 下载到内存 → `h264_qsv`，30 帧 | 30 帧每秒 | 约 1.6 个核 |
| 桌面复制 → 下载到内存 → `libx264 ultrafast`，30 帧 | 30 帧每秒 | 约 2.5 个核 |
| GDI，只采集 | 29 帧每秒 | 约 0.5 个核 |

结论：

- 有活动显示器时，桌面复制加显存内硬件编码可以到 55 帧以上，只占四分之一个核。这是首选管线。
- 画面一旦下载到内存，颜色转换的开销就成了主要成本（同样 60 帧，CPU 相差十倍以上），所以硬件编码必须走显存内路径。
- 合盖状态下瓶颈在采集：系统不合成画面，桌面复制没有帧可给，GDI 上限约 16 帧每秒（亮屏时 GDI 也只有 29 帧）。
- 编码不是瓶颈，硬件与软件编码器的能力都远超需要。

合盖状态下的三种出路：

| 方式 | 帧率 | 代价 |
| --- | --- | --- |
| GDI 采集 | 约 16 帧每秒（实测） | 无需安装任何东西，现在就能用 |
| 虚拟显示驱动 | 预计 30 到 60 帧（未测） | 需要以管理员安装一个驱动；RustDesk 的做法 |
| HDMI 假负载（插在接口上的小硬件） | 预计 30 到 60 帧（未测） | 需要买一个硬件，不用装驱动 |

| 桌面复制放在滤镜图里，画面下载到内存，`libx264` | 3 到 92 毫秒，中位 69 |
| GDI 采集，`h264_qsv` | 59 到 113 毫秒，中位 81 |
| 桌面复制放在滤镜图里，显存内直接交给 `h264_qsv` | 290 到 412 毫秒；机器负载高时 23 到 759 |
| 桌面复制作为输入设备（`-f lavfi -i`），显存内直接交给 `h264_qsv` | 20 到 970 毫秒，每次点击都不同 |
| 桌面复制作为输入设备，`libx264` | 中位 658 毫秒 |

结论：

- 延迟来自两处，都在 ffmpeg 内部：把采集当作输入设备会多出几百毫秒；把显存里的帧直接交给硬件编码器会再多出几百毫秒且不稳定。两处的具体原因没有查明，只确认了绕开它们之后延迟降到 60 毫秒左右。
- 因此 3.4 里"首选显存内硬件编码"的结论作废：它省 CPU（四分之一个核），但延迟不可用。现在的首选是"下载到内存再硬件编码"，代价是 30 帧时约 1.6 个核、60 帧时约 3.3 个核（3.4 的数字），所以默认 30 帧。
- 码率控制从固定码率改为可变码率：固定码率会把每一帧都填充到相同大小，静止画面也占满码率。

经过浏览器的端到端延迟（Chrome 无头模式，亮屏，各点击 30 次；"显示"指浏览器预计把变化的那一帧显示出来的时刻）：

| 管线与档位 | 帧到达浏览器 | 显示 | 实际帧率 |
| --- | --- | --- | --- |
| 旧管线（输入设备加显存内编码），30 帧 | 中位 954 毫秒 | 中位 1061 毫秒 | 30 |
| 新管线，30 帧 | 中位 54，90% 在 77 以内 | 中位 107，90% 在 140 以内，最大 1062（1 次） | 23 |
| 新管线，60 帧 | 中位 56，90% 在 116 以内 | 中位 88，90% 在 121 以内，最大 184 | 33 |

未查明的两点：30 帧档那一次超过 1 秒的异常值；实际帧率低于请求值（测试画面基本静止，可能是没有新画面可采，也可能是管线跟不上）。

## 5. 方案设计

### 5.1 总体结构

```text
浏览器（Chrome / Edge）
  /remote/ 页面
  ├─ <video>          ← 视频轨道（H.264，RTP，UDP）
  ├─ 数据通道 input   → 鼠标、键盘事件
  └─ 数据通道 control ⇄ 光标形状、剪贴板、状态、统计
        │  建立：POST /v1/remote/sessions（一次 SDP 交换）
        ▼
vm-agent
  internal/api/remote.go        建立、列出、关闭会话
  internal/actions/remote       会话管理、WebRTC、输入分发、光标与剪贴板推送
    ├─ 编码器（随会话启停）
    │    ffmpeg：采集 → H.264 → 标准输出 → 拆成帧 → 写入视频轨道
    ├─ 输入：数据通道消息 → 现有 input.Backend
    └─ 光标 / 剪贴板：轮询变化 → 数据通道
```

一个会话对应一个浏览器标签页，同一时间只有一个会话（5.12）。会话建立时启动 ffmpeg，结束后停止，空闲时不占资源。

### 5.2 传输选型

| | A. WebRTC 媒体轨道（推荐） | B. WebSocket 加 WebCodecs | C. WebSocket 加 MSE |
| --- | --- | --- | --- |
| 浏览器端解码 | `<video>` 自带，硬解 | 自己调解码器、自己画到 canvas | `<video>` 自带 |
| 延迟 | 低；有抖动缓冲，可调到最小 | 最低；收到即解码 | 较高，缓冲难以压到 100 毫秒以内 |
| 丢包（笔记本走 Wi-Fi） | 重传与关键帧请求内建 | TCP 队头阻塞，丢包时卡顿 | 同 B |
| 是否需要 HTTPS | 不需要 | 需要（WebCodecs 只在安全上下文可用） | 不需要 |
| Go 侧依赖 | pion/webrtc，纯 Go，约二十个子模块，二进制增大数 MB | 一个 WebSocket 库 | 一个 WebSocket 库，另需封装 fMP4 |
| 色度 | 硬件编解码路径是 4:2:0；4:4:4 是否可用取决于浏览器，未验证 | 可用 4:4:4（AV1 或 VP9），文字更清晰 | 4:2:0 |
| 信令 | 一次 HTTP 请求即可，符合现有同步模型 | 长连接 | 长连接 |

推荐 A：在不做 TLS 的前提下就能用，对 Wi-Fi 丢包更稳，浏览器端代码最少。编码管线与传输解耦，以后需要 4:4:4 清晰度时可以加 B 作为第二条通道。

网络细节：局域网只用主机候选地址，不配 STUN 与 TURN；固定一个 UDP 端口（默认 7071）便于防火墙放行；ICE 候选一次收齐后随应答返回，不做增量交换。

### 5.3 视频管线

Windows：

```text
ffmpeg -init_hw_device d3d11va -f lavfi -i ddagrab=output_idx=N:framerate=30:draw_mouse=0
       → 硬件帧直接交给 h264_qsv（或 h264_nvenc、h264_amf）
       → 低延迟参数：无 B 帧、无前瞻、异步深度 1
       → -f h264 pipe:1
```

采集方式在运行时选择，不在启动时写死：

1. 有活动显示器时用 `ddagrab`（桌面复制）。启动后 2 秒内拿不到第一帧就判定不可用，改用下一种。
2. 否则用 `gdigrab`。这是合盖且没有虚拟显示器时的路径，约 16 帧每秒。
3. 显示状态变化（开盖、合盖、接入显示器、虚拟显示器启停）时重新选择并重启采集。

编码器优先 `h264_qsv` 等硬件编码器，不可用时用 `libx264 ultrafast zerolatency`。启动时试编一小段来确认，不只看编码器列表。

| 参数 | 初始值 | 说明 |
| --- | --- | --- |
| 帧率 | 30，可选 60 | |
| 码率 | 2560×1600 用 8 Mbps，上限 20 Mbps | RustDesk"最佳"档在该分辨率约 5 Mbps；局域网可以给更多 |
| 关键帧间隔 | 2 秒 | ffmpeg 命令行无法按需出关键帧，所以用短间隔；丢包后最多 2 秒恢复画面 |
| 配置 | H.264 High 或 Main，4:2:0 | 以浏览器实际能硬解的为准，需实测 |
| 光标 | 不画进视频 | 由网页本地绘制，见 5.5 |

Go 侧读取 ffmpeg 标准输出的 Annex B 码流，按访问单元切分后写入 pion 的视频轨道。ffmpeg 子进程沿用录屏的进程树管理，服务退出时一并清理。

延迟估计（未实测，指有活动显示器、走桌面复制的情况）：采集等待不超过一帧（30 帧时 33 毫秒）、编码 5 到 15 毫秒、局域网 1 到 5 毫秒、浏览器缓冲与解码 20 到 50 毫秒、显示刷新 8 到 16 毫秒，合计约 70 到 120 毫秒；60 帧时更低。合盖走 GDI 时每帧间隔约 60 毫秒，延迟相应增加。

### 5.4 输入

数据通道分两条：

- `input`（可靠有序）：按键、鼠标按键、滚轮、文本。
- `pointer`（不可靠、不重传）：鼠标移动。过期的移动没有重发价值，丢了由下一条覆盖。

消息用紧凑 JSON，例如 `{"t":"kd","c":"KeyA"}`、`{"t":"mm","x":1280,"y":800}`。

| 事项 | 设计 |
| --- | --- |
| 坐标 | 网页把视频元素内的位置换算成远端物理像素（加显示器原点偏移），服务端不做缩放 |
| 鼠标移动 | 浏览器端按帧合并，每帧最多发一条；服务端只执行队列里最新的一条 |
| 拖拽 | 用指针捕获，拖出视频区域也不丢事件 |
| 滚轮 | 传像素增量，服务端换算成系统的滚轮增量并累积小数部分，触控板滚动保持顺滑 |
| 按键 | 传 `KeyboardEvent.code`（位置码），服务端映射到现有键表，Windows 按扫描码注入 |
| 文本 | 输入法上屏的文字作为文本消息，走现有的 Unicode 注入 |
| Mac 键盘 | Command 默认映射为 Ctrl（Cmd+C、Cmd+V 等按习惯工作），工具条上可切换为 Win 键。macOS 在按住 Command 时不上报其他键的抬起，页面在 Command 抬起时补发 |
| 卡键 | 服务端按会话记录已按下的键与鼠标按键；页面失焦、数据通道关闭或会话结束时全部释放 |
| 与 Agent 并存 | 每个实时事件短暂持有现有输入队列的锁，和 `input/*` 接口的动作互不穿插 |

### 5.5 光标

服务端每 30 毫秒左右查询一次光标句柄；形状变化时取图像，经 `control` 通道发送 PNG 与热点坐标；网页把它设为视频区域的 CSS 光标。这样鼠标移动由本机浏览器绘制，没有视频延迟。

画面按比例缩小显示时，光标图像同比例缩放。浏览器对自定义光标有尺寸上限（Chrome 为 128×128），超出时退回把光标画进视频。

远端光标被别的来源移动时（Agent 在操作，或有人在用实体鼠标），服务端推送位置，网页在画面上叠加一个标记。

### 5.6 剪贴板

- 远端到本地：服务端轮询剪贴板变化（Windows 可用剪贴板序号，无需读内容），文本变化时推送到网页。
- 本地到远端：粘贴时网页把本机剪贴板文本先写入远端剪贴板，再发送 Ctrl+V。
- 防回环：服务端记住自己最后写入内容的摘要，读到相同内容不回推。

浏览器的自动读写剪贴板接口只在安全来源下可用，按 8.1 第 2 条在 Chrome 里标记一次即可；未标记时退化为：本地到远端靠粘贴事件，远端到本地需要在页面上点一下"复制"。

### 5.7 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/remote/` | 网页（内嵌静态文件） |
| POST | `/v1/remote/sessions` | 请求：`sdp`（浏览器的 offer）、`display`、`fps`、`bitrate_kbps`、`holder`（使用者名称）。已被占用时返回 `conflict` 并附占用者与起始时间。响应：`session_id`、`sdp`（answer）、显示器信息 |
| GET | `/v1/remote/sessions` | 当前会话：使用者、来源地址、开始时间、最近一次输入时间、帧率、码率 |
| DELETE | `/v1/remote/sessions/{id}` | 关闭会话 |

启动参数：

```text
-remote                启用网页远程桌面
-remote-udp-port       WebRTC 使用的 UDP 端口，默认 7071
-remote-idle-release   使用者无操作多久后自动释放使用权，默认 10m
```

`capabilities.actions` 在可用时增加 `remote`。可用的条件：已启用、ffmpeg 可用且至少一种采集编码组合试编成功、有桌面会话。

审计：会话建立与关闭各记一条（使用者、来源、时长、按键与鼠标事件计数），不记录按键内容。

### 5.8 网页端

单个 HTML 文件加一份脚本，不引入前端框架与构建工具，随二进制内嵌。

- 顶部工具条（可自动隐藏）：机器名、延迟与帧率、画质、显示器选择、适应窗口与原始大小、全屏、发送组合键、剪贴板、释放使用权。
- 全屏时请求键盘锁，捕获 Win、Alt+Tab、Esc 等系统键（需要按 8.1 第 2 条在 Chrome 里标记一次）。
- 断线后自动重连，重连期间保留最后一帧并提示。
- 统计来自 WebRTC 自带的数据：帧率、码率、丢包、解码耗时、抖动缓冲时长。

### 5.9 多机入口

目标是"一个页面管所有机器"。方案：页面里维护一份机器列表（名称加地址），以卡片显示每台机器的缩略图（复用现有 `screen/capture`，每几秒一张小图），点击进入实时会话，多台可以用页内标签同时打开。

列表与页面由谁提供有三种做法，到该阶段再定：

| 做法 | 说明 |
| --- | --- |
| 任选一台 agent 作入口 | 该 agent 配置其他机器的地址，并代理它们的信令请求；视频仍然是浏览器与目标机器直连 |
| 在观看的电脑上运行入口 | `vm-agent` 能在 macOS 上编译（没有实际运行验证过），以"仅入口"模式提供页面与代理，不操作本机 |
| 不做入口 | 每台机器各开一个标签页，收藏夹管理 |

### 5.10 与现有设计的关系

| 现有约定 | 影响 |
| --- | --- |
| D3：Windows 零运行时依赖，录屏依赖 ffmpeg | 远程桌面同样依赖 ffmpeg，没有 ffmpeg 时该能力不上报 |
| D8：接口同步，长操作用标识 | 相符：建立会话是一次同步请求，会话本身按标识管理 |
| D9：不做鉴权与 TLS | 沿用；网页不带来新的暴露面（同一端口本来就能执行任意命令），但更容易被人顺手打开 |
| 4.1：以桌面用户身份运行 | 主进程不变；阶段 4 新增服务与会话内助手，spec 4.1 需要修订（5.14） |
| 4.4：优雅关闭 | 关闭时先断开远程会话并停止编码器，再走现有顺序 |
| 纯 Go、`CGO_ENABLED=0` | 保持；pion 是纯 Go |
| `openapi.yaml` 与生成的客户端 | 新接口需要补进规格并重新生成 |

### 5.11 合盖与虚拟显示器

背景见 3.4：合盖后没有活动显示器，系统不合成画面。

分两步：

1. 基础路径（已实现）：自动回退到 GDI 采集，约 16 帧每秒，不需要安装任何东西。页面上显示当前的采集方式和实际帧率。
2. 流畅路径（阶段 3，本节）：安装一个虚拟显示驱动（Windows 的间接显示驱动，IDD）。远程会话开始时如果没有活动显示器，就启用一个虚拟显示器；会话结束后停用。有了活动显示器，系统恢复合成，桌面复制采集可用。

#### 推荐：Amyuni `usbmmidd`

理由：

- 签名是微软硬件兼容签名，安装时不需要向系统导入第三方证书。对一个放进别人机器的组件，这是最重要的一条。
- 启停只是一个控制码，适合"会话开始时加、结束时减"。
- RustDesk 已在大量机器上用它，行为有据可查。
- 没有额外的运行库依赖。

代价：闭源，2021 年后没有更新；分辨率只能从预设档里选，没有 2560×1600，需要在安装时把这台机器的面板分辨率写进它的注册表档位；许可证里有一句关于广告的条款，实际会不会出现广告没有验证过。

备选：如果它在 Windows 11 新版本上装不上或不出帧，换用 Virtual Display Driver，接受导入证书这一步。

#### 分发方式

驱动文件不放进本仓库，也不内嵌进 `vm-agent`。由安装脚本从厂商地址下载，校验固定的 SHA-256 后安装，许可证文件随驱动一起保留在安装目录。这样本项目不承担再分发，许可证的致谢要求写在部署文档里即可。

#### 安装与卸载

需要管理员权限，各一条命令，由新增的脚本 `deploy/windows/virtual-display.ps1` 完成：

| 动作 | 做什么 |
| --- | --- |
| 安装 | 下载并校验驱动包；用系统的即插即用接口安装（创建一个根枚举的显示适配器设备）；在驱动的注册表项里加入本机面板分辨率 |
| 卸载 | 移除所有虚拟显示器；删除该设备；删除驱动包；删除下载的文件 |

系统里留下的东西：设备管理器"显示适配器"下的一个"USB Mobile Monitor Virtual Display"、驱动存储区里的一个驱动包、`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\WUDF\Services\usbmmIdd` 下的参数。不装服务，不改启动项。

#### 运行时行为

| 事项 | 设计 |
| --- | --- |
| 何时启用 | 会话开始时没有活动显示器（现有的合成检测）且驱动已安装，就加一台虚拟显示器；驱动没装则照旧走 GDI |
| 何时停用 | 会话结束时移除本会话加上的那一台；服务启动时清理上次异常退出遗留的 |
| 亮屏时 | 不启用，行为与现在完全相同 |
| 分辨率 | 默认取本机面板的分辨率，使窗口布局不变 |
| 会话中开盖 | 内屏恢复后移除虚拟显示器，回到内屏 |
| 权限 | 驱动的设备接口允许普通权限打开（其安装文件里的安全描述符如此），所以运行时不需要提权；这一点要在安装后实测确认 |
| 采集目标 | 现在固定采集第 0 个输出；虚拟显示器成为唯一活动输出时它是不是第 0 个，要实测 |

#### 风险与未知

- 最大的未知：加了虚拟显示器之后，合盖状态下系统是否恢复画面合成、桌面复制是否出帧。这是 RustDesk 等工具的通行做法，但没有在这台机器上验证过；笔记本上已有的 MuMu 虚拟显示驱动没有让合成恢复，原因是它当前没有暴露显示器。
- 该驱动在 Windows 11 build 26300 与内存完整性开启的情况下能否安装。它的说明文件写的是"仅 Windows 10"，RustDesk 在 Windows 11 上使用它。
- 显示器拓扑变化的副作用：加减显示器时，系统可能移动窗口、改变缩放比例；合盖时内屏是否仍算"已连接"决定了虚拟显示器是成为唯一屏还是扩展屏。
- 驱动出问题时的恢复手段：在设备管理器里卸载该设备，或运行卸载脚本；它不是显卡驱动，不参与开机显示，理论上不会导致无法进入桌面，但没有验证。

#### 实施结果（2026-11-17 至 18）

已在测试用笔记本上实现并验证，数据见 3.6。

- 安装：`deploy/windows/virtual-display.ps1 -Action install -Width 2560 -Height 1600`，需要管理员权限。在 Windows 11 build 26300、内存完整性开启的情况下安装成功，设备状态正常。
- 卸载：同一脚本的 `-Action uninstall`。实测卸载后设备、驱动包、驱动文件、下载目录与注册表参数全部移除，重复执行无副作用，之后可以重新安装。
- 运行时不需要管理员权限：`vm-agent` 以普通权限打开驱动的设备接口，加减显示器、设置分辨率与缩放都成功。
- 最大的未知已经成立：合盖时加一台虚拟显示器，系统恢复画面合成，桌面复制出帧。

实现与设计的出入：

| 事项 | 实际情况 |
| --- | --- |
| 默认分辨率 | 写进驱动注册表的默认值不生效，第一次插上是 1024×768。改为插上后由 `vm-agent` 设置分辨率；系统会记住同一台显示器的设置，之后再插就是对的 |
| 缩放 | 虚拟显示器默认 100%，需要设成与面板一致（150%）。用的是"设置"应用所用的未公开接口（`DisplayConfigSetDeviceInfo` 的类型 -4） |
| 取什么尺寸 | 没有活动显示器时系统报告的桌面尺寸与缩放不可靠（重装驱动后报告过 200%、1280×800）。因此在真实显示器亮着时把它的尺寸与缩放记到状态目录的 `remote-display.json`，虚拟显示器用记录的值 |
| "显示器是否插着" | 适配器输出的"已连接到桌面"标志在最后一台显示器拔掉后仍然为真，要看该输出下的显示器设备是否处于活动状态 |
| 异常退出 | 加了显示器就在状态目录写一个标记文件；启动时若标记存在，把遗留的虚拟显示器拔掉。没有标记的虚拟显示器（别的程序或用户自己加的）不动 |
| 鼠标指针 | 虚拟显示器没有硬件光标，系统把指针直接画进画面，采集到的视频里带着指针；网页再画一个本地光标就成了两个。现在虚拟显示器是唯一显示器时通知网页隐藏本地光标，只用画面里的那个，代价是合盖时指针移动跟随视频延迟（约 100 毫秒）。这个原因是按该类驱动的通行行为推断的，修复没有在真机合盖状态下确认 |
| 会话中开盖、合盖 | 实现了跟随：真实显示器回来就拔掉虚拟的，最后一台显示器消失就加上。只有单元测试，没有在真机上开合盖验证 |

没有验证的：

- 会话进行中开盖与合盖的实际表现，以及开盖后内屏与虚拟显示器并存时的排列。
- 许可证里提到的广告页面是否会出现。安装与使用过程中没有看到，但笔记本合着盖，没有人看屏幕。
- 长时间插着虚拟显示器的稳定性；每次会话都加减一次显示器对桌面上其他程序的影响（窗口位置在实测中保持不变，因为尺寸与缩放一致）。
- NVIDIA、AMD 显卡的机器，以及多台真实显示器的机器。

### 5.12 使用权

同一时间只有一个使用者，先到先得，用完释放后别人才能用。

| 事项 | 设计 |
| --- | --- |
| 占用 | 建立会话即占用；请求里带使用者名称（网页首次打开时填写，存在浏览器里） |
| 被占用时 | 新的连接请求返回 `conflict`，页面显示"某某自几点起正在使用"，并定时重试或等待通知 |
| 释放 | 使用者点"释放"、关闭页面、断线超过 30 秒，或超过 `-remote-idle-release` 没有任何输入 |
| 强制释放 | `DELETE /v1/remote/sessions/{id}`，用于占用者忘记释放的情况；因为没有鉴权，任何能访问端口的人都能调用 |
| Agent 的输入接口 | 有人占用期间，`input/*` 返回 `conflict`、`details.reason=remote_in_use`；截图等只读接口不受影响 |

### 5.13 声音

已实现（阶段 2）。采集系统正在播放的声音，单向传到浏览器。

- 采集：Go 通过 COM 调用 WASAPI 环回采集默认播放设备（`internal/platform/win/loopback_windows.go`，不用 cgo），请求 16 位 PCM。没有声音播放时系统不给数据，采集端按时钟补静音，保持音频流连续。
- 编码：PCM 经管道交给 ffmpeg 编成 Opus（低延迟模式，10 毫秒一帧，96 kbps），以 RTP 发回本机端口，再写入 WebRTC 音频轨道。
- 浏览器：声音用独立的 `<audio>` 元素播放，不与画面绑定，避免音画同步机制拖慢画面。浏览器要求用户在页面上操作过才允许出声，工具条上有声音开关。
- 播放设备变化（插拔耳机等）时重新开始采集。
- 声音是可选的：采集失败时会话照常进行，只是没有声音。
- 远端本机会同时出声；"让远端静音"没有做。

### 5.14 锁屏

第一版已实现并在测试用笔记本上验证（2026-11-18）：锁屏界面能在网页上看到并操作。范围比最初设想的小，见"有意不做的"。

```text
vm-agent -desktop-service（Windows 服务，SYSTEM，Session 0）
   │ 把自己的令牌复制一份、改到控制台会话，CreateProcessAsUser，桌面指定为 winsta0\Winlogon
   ▼
vm-agent -desktop-helper（SYSTEM，运行在用户会话内的 Winlogon 桌面上）
   │ 命名管道 \\.\pipe\vm-agent-desktop-<会话号>，只允许 SYSTEM 与该会话的登录用户连接
   ▼
vm-agent（桌面用户身份，现有主进程）
```

| 事项 | 实现 |
| --- | --- |
| 安装与卸载 | `deploy/windows/secure-desktop.ps1 -Action install|uninstall|status`，需要管理员权限。安装时把 `vm-agent.exe` 与 ffmpeg 复制到 `%ProgramFiles%\vm-agent`，服务从那里运行：SYSTEM 进程不能执行普通用户可以改写的文件 |
| 服务 | 每秒检查一次：控制台会话变了或助手退出了，就在当前控制台会话里重新启动助手。除此之外什么都不做 |
| 助手只做两件事 | 把输入事件注入当前接收输入的桌面；用 ffmpeg 的 GDI 采集把自己所在的桌面编码成 RTP 发到本机端口。助手不执行调用方给的任何命令，ffmpeg 的路径来自服务自己的命令行，进入命令行的参数都是校验过范围的数字 |
| 平时 | 不经过助手，采集与输入照旧由主进程完成 |
| 锁屏时 | 主进程发现输入桌面不是 Default，且助手可用：视频改由助手提供，输入事件转发给助手；解锁后自动切回 |
| 网页 | 锁屏时不再显示"无法操作"的遮罩；没装服务时仍然显示。画面里带着指针，本地光标隐藏 |
| 锁屏时建立会话 | 允许；`capabilities.actions` 在锁屏且助手可用时仍含 `remote` |
| Agent 的输入接口 | 不变：锁屏时 `input/*`、`screen/*` 仍返回 `no_display`。助手只服务于网页远程桌面 |

实测（合盖，虚拟显示器 2560×1600）：锁屏后约 2 到 3 秒画面切换到锁屏界面，16 到 18 帧；从网页发一个按键，密码框里出现一个圆点，再发退格键，圆点消失。浏览器缓冲在 250 到 600 毫秒，比平时的桌面画面慢，原因没有查（锁屏走的是 GDI 采集加软件编码）。输入正确密码完成解锁这一步没有由我测试，因为我不知道密码。

有意不做的：

- UAC 提权弹窗的安全桌面。它与锁屏用的是同一个桌面，技术上助手同样能采集和注入，但那样等于让任何以该用户身份运行的程序都能通过管道替用户点"是"，UAC 的隔离就没有了。锁屏不同：不知道密码，能输入也解不开。所以助手只在会话确实处于锁定状态（会话管理器的记录，`WTSSessionInfoEx`）且没有提权弹窗进程（`consent.exe`）时才工作，其余时候拒绝采集与输入；状态读不出来时按未锁定处理。实测未锁定时直接连管道：视频请求被拒绝，鼠标移动没有被执行。
- Ctrl+Alt+Del。Windows 10 与 11 的锁屏不需要它（按任意键或点击即可进入密码输入），需要它的只有启用了"安全登录"策略的机器。要支持得由服务调用 `SendSAS`。
- 没有用户登录时的登录界面。那时主进程不存在，没有人提供网页与会话。
- 用锁屏界面上的本机输入法输入：文字作为 Unicode 字符注入，密码框能接受；没有测试过中文。

安全上的含义：

- 装了服务之后，能访问 `vm-agent` 端口的人就能看到锁屏界面并往里输入。`vm-agent` 没有鉴权（D9），所以这台机器的锁屏只剩下密码本身这一道防线，而且可以被远程无限次尝试（Windows 自身的锁定策略仍然生效）。
- 机器上多了一个开机自启的 SYSTEM 服务和一个 SYSTEM 助手进程。它们的攻击面是那条命名管道，只有登录用户与 SYSTEM 能连接。
- 与 spec 4.1（"不可采用 Windows 服务"）的关系：服务不承载业务逻辑，业务仍在用户身份的主进程里；spec 需要相应修订。

真人验证（2026-11-18）：合盖状态下从网页连接锁着的笔记本，输入密码后解锁成功，画面自动切回桌面复制采集。那次会话里声音没有送出，原因没有查明；会话在未锁定状态下开始时声音正常。

没有验证的：加上"只在锁屏时工作"的限制之后，锁屏状态下助手是否照常工作（只验证了未锁定时会拒绝）；锁屏状态下长时间连接；快速切换用户、注销、RDP 登入登出时服务是否正确地重启助手；卸载脚本。

## 6. 已知限制

| 限制 | 原因 | 缓解 |
| --- | --- | --- |
| 合盖且没有装虚拟显示驱动时只有约 16 帧每秒 | 系统不合成画面，只能用 GDI 采集（3.4 实测） | 用 `deploy/windows/virtual-display.ps1` 安装虚拟显示驱动（5.11） |
| 没装锁屏支持服务时，锁屏界面看不到也点不了；登录界面（无人登录）与 UAC 弹窗始终不支持 | 普通用户进程无法访问安全桌面 | 用 `deploy/windows/secure-desktop.ps1` 安装服务（5.14） |
| 管理员权限的窗口点不了 | Windows 的完整性级别隔离 | 用 `-RunLevel Highest` 安装 |
| 文字边缘不如 RustDesk 锐利 | 硬件 H.264 编解码是 4:2:0 色度，RustDesk 可用 4:4:4 | 原生分辨率加高码率；后续加 WebCodecs 4:4:4 通道 |
| Ctrl+Alt+Del 发不了 | 该组合键只有系统服务调用 `SendSAS` 才能注入，没有做 | 替代：Ctrl+Shift+Esc 开任务管理器 |
| 非全屏时 Ctrl+W、Ctrl+T、Alt+Tab 等被浏览器或本机系统拿走 | 浏览器限制；RustDesk 的原生客户端用全局键盘钩子，没有这个问题 | 全屏加键盘锁；工具条按钮代发 |
| 画质与码率切换有一瞬间卡顿 | ffmpeg 命令行运行中改不了参数，只能重启 | 可接受；将来自己调编码器接口才能消除 |
| 严重丢包后最多 2 秒才恢复画面 | 无法按需出关键帧 | 同上 |
| DRM 保护内容与独占全屏游戏可能黑屏 | 桌面复制接口的限制 | 无 |
| 不支持 Linux | 本期范围外 | |

## 7. 分阶段计划与验收

## 9. 未验证的假设

以下内容来自推断，没有实测或没有在源码里确认：

- 合盖状态下两种延迟测法结果不一致的原因（3.6），以及该状态下换用 `libx264` 是否更快。
- 30 帧档偶发的超过 1 秒的延迟，以及实际帧率低于请求值的原因。
- 显存内硬件编码路径延迟大的原因，以及是否有办法既省 CPU 又低延迟（例如自己调用编码器接口而不经过 ffmpeg）。
- Chrome 能通过 WebRTC 硬解 2560×1600 的 H.264；如果不能，需要降分辨率或换编码。
- 浏览器在 `http://` 的局域网地址上允许建立只接收的 WebRTC 连接（5.2 表中"不需要 HTTPS"一项）。
- 有 MuMu 虚拟显示适配器存在时，`ddagrab` 能正确选到核显上的真实输出。
- 在安全桌面上用 GDI 采集并注入输入的具体做法（5.14），以及 ffmpeg 子进程在该桌面上的行为。
- 声音与画面的同步程度，以及声音的端到端延迟：只验证了声音流能到达（3.7），没有测时间差。
- pion 加进来后二进制的实际增量。
- CSS 自定义光标在 150% 缩放的 Windows 光标尺寸下显示正常。
- RustDesk 的默认键盘模式：源码里确认了三种模式及其含义，没有确认默认值是哪一种。
- RustDesk 网页端的实现方式：其源码不在开源仓库里，本文没有引用它的做法。
